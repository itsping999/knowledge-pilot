# 企业源代码安全管理规范

## 文档信息
- 文档编号：SEC-SCA-001
- 版本：1.0
- 适用范围：企业所有源代码仓库、CI/CD 流水线和代码评审流程

## 1. 代码仓库安全管理

### 1.1 仓库访问控制
代码仓库应实施基于角色的访问控制，角色分为只读、开发者、维护者和管理员四个级别。核心业务代码仓库的写入权限应经过部门负责人审批。外部协作者的访问权限应设置有效期，最长不超过九十天，到期后需重新审批。仓库应启用分支保护规则，主分支和发布分支的合并应经过至少两名开发者的代码评审。

### 1.2 代码仓库审计
代码仓库应记录以下操作的审计日志：
- 代码推送和分支操作（创建、删除、合并）
- 权限变更（成员添加、移除和角色修改）
- 仓库设置变更（保护规则、可见性、Webhook）
- 敏感操作（强制推送、历史重写、仓库删除）

审计日志应保留三百六十五天以上，并与企业安全信息和事件管理（SIEM）系统集成。

## 2. 敏感信息防泄漏

### 2.1 禁止提交的敏感信息
以下类型的信息不得提交到代码仓库：
- 数据库连接字符串和密码
- API 密钥、访问令牌和会话密钥
- SSL/TLS 证书私钥和 SSH 私钥
- 加密密钥和初始化向量
- 内部 IP 地址和网络拓扑信息
- 员工个人信息和客户数据

### 2.2 敏感信息检测
企业应在代码仓库中部署敏感信息检测工具（如 GitLeaks、TruffleHog），在以下环节实施检测：
- 预提交钩子（pre-commit hook）：在开发者本地提交前进行检测
- CI 流水线：在代码推送后自动扫描提交历史
- 定期全量扫描：每周对所有仓库进行一次全量扫描

发现敏感信息泄漏后应立即吊销泄漏的凭据，清理 Git 历史中的敏感信息，并通知安全团队评估影响范围。

## 3. 依赖安全管理

### 3.1 开源组件引入审批
引入新的开源组件前应经过以下评估：
- 组件许可证是否与企业商业许可兼容
- 组件的维护状态（最近更新时间、活跃贡献者数量）
- 组件已知漏洞数量和严重程度
- 组件的下载量和社区活跃度
- 是否存在替代方案

### 3.2 依赖漏洞扫描
CI/CD 流水线应集成软件成分分析（SCA）工具，每次构建时自动扫描项目依赖的已知漏洞。严重漏洞应阻断构建流程，高危漏洞应在七天内修复，中危漏洞应在三十天内修复。企业应维护内部依赖漏洞知识库，跟踪每个项目的漏洞修复进度。

### 3.3 依赖版本锁定
所有项目应使用锁文件（如 package-lock.json、Cargo.lock、go.sum）锁定依赖版本。依赖更新应通过自动化工具（如 Dependabot、Renovate）创建 Pull Request，经过测试和评审后合并。禁止使用 latest 或 * 等浮动版本号。

## 4. 静态应用安全测试（SAST）

### 4.1 SAST 工具集成
CI/CD 流水线应集成静态代码分析工具，在每次代码提交时自动执行安全扫描。SAST 工具应覆盖 OWASP Top 10、CWE Top 25 和企业特定的安全编码规范。扫描结果应自动关联到代码评审流程，高危问题应在合并前修复。

### 4.2 安全编码规范
企业应制定并维护安全编码规范，覆盖以下常见安全问题：
- 输入验证和输出编码
- SQL 注入和命令注入防护
- 跨站脚本（XSS）防护
- 认证和授权实现
- 加密算法使用规范
- 错误处理和日志记录
- 文件上传和路径遍历防护

### 4.3 代码评审安全检查
代码评审应包含以下安全检查项：
- 是否存在硬编码的敏感信息
- 是否对用户输入进行了充分验证
- 是否使用了不安全的函数或 API
- 是否正确实现了权限校验
- 是否对异常情况进行了安全处理

## 5. 代码仓库备份与恢复

### 5.1 备份策略
所有代码仓库应实施定期备份，备份频率为每日一次增量备份、每周一次全量备份。备份数据应存储在与代码仓库不同的物理位置或云区域。备份数据应加密存储，加密密钥由密钥管理系统管理。

### 5.2 恢复测试
代码仓库备份恢复应每季度进行一次演练，验证备份数据的完整性和可用性。恢复演练应记录恢复时间、数据完整性和发现的问题。恢复演练结果应纳入安全审计报告。

# 星河制造集团日志分析平台建设规范（样例）

## 1. 总则

为建立统一的日志收集、存储、分析和告警平台，提升安全运营、运维监控和合规审计能力，依据《网络安全法》《数据安全法》和等级保护 2.0 要求，结合集团数字化建设规划，制定本规范。本规范适用于集团所有信息系统的日志采集、传输、存储、分析和销毁管理。

## 2. 平台架构

### 2.1 总体架构

日志分析平台采用分层架构设计：

1. 采集层：通过 Agent、Syslog、API 和文件采集等方式收集各类日志。
2. 传输层：通过 Kafka 消息队列实现日志的可靠传输和缓冲。
3. 存储层：采用 Elasticsearch 集群存储日志数据，支持全文检索和聚合分析。
4. 分析层：提供实时流式分析和离线批量分析能力。
5. 展示层：提供可视化仪表盘、报表和告警通知。

### 2.2 采集范围

日志分析平台应采集以下类型的日志：

1. 操作系统日志：Windows 事件日志、Linux Syslog、系统调用审计日志。
2. 网络设备日志：路由器、交换机、防火墙、WAF 和负载均衡器日志。
3. 应用系统日志：Web 服务器访问日志、应用业务日志、错误日志和调试日志。
4. 数据库日志：数据库审计日志、慢查询日志和错误日志。
5. 安全设备日志：IDS/IPS 日志、终端安全日志和 DLP 告警日志。
6. 云平台日志：云资源操作日志、API 调用日志和安全审计日志。
7. 终端日志：终端行为日志、USB 接入日志和打印日志。

### 2.3 采集方式

日志采集应采用以下方式：

1. Agent 采集：在服务器和终端安装轻量级 Agent，实时采集日志。
2. Syslog 接收：通过 Syslog 协议接收网络设备和安全设备日志。
3. API 采集：通过 REST API 采集云平台和 SaaS 应用日志。
4. 文件采集：定时采集应用系统产生的日志文件。
5. 数据库采集：通过数据库连接器采集审计日志和变更日志。

## 3. 日志标准化

### 3.1 统一字段定义

所有日志应标准化为统一格式，包含以下必填字段：

1. timestamp：日志产生时间，统一使用 ISO 8601 格式。
2. source：日志来源，包含主机名、应用名和组件名。
3. level：日志级别，分为 DEBUG、INFO、WARN、ERROR 和 FATAL。
4. category：日志类别，分为 SECURITY、AUDIT、OPERATION 和 BUSINESS。
5. event_id：事件标识符，用于关联同一事件的多条日志。
6. user：操作用户，包含用户名和用户 ID。
7. action：操作动作，如 LOGIN、LOGOUT、CREATE、UPDATE、DELETE。
8. resource：操作对象，包含资源类型和资源标识。
9. result：操作结果，分为 SUCCESS 和 FAILURE。
10. message：日志消息，包含详细描述。

### 3.2 数据清洗

日志采集后应进行以下数据清洗：

1. 格式解析：解析不同格式的日志，提取标准化字段。
2. 字段映射：将原始字段映射到标准化字段。
3. 数据校验：校验字段值的合法性和完整性。
4. 去重处理：去除重复的日志记录。
5. 富化处理：补充 IP 地理信息、资产信息和威胁情报。

### 3.3 时间同步

所有系统应配置 NTP 时间同步，确保日志时间的一致性：

1. NTP 服务器：使用集团统一的 NTP 服务器。
2. 时区统一：所有日志时间统一转换为北京时间。
3. 精度要求：时间同步精度不低于毫秒级。

## 4. 日志存储

### 4.1 存储策略

日志存储应采用分级存储策略：

1. 热存储（0-30 天）：存储在高性能 SSD 上，支持实时查询。
2. 温存储（30-180 天）：存储在普通 HDD 上，支持历史查询。
3. 冷存储（180 天-3 年）：压缩存储在对象存储中，支持归档查询。
4. 离线存储（3 年以上）：备份到磁带或冷存储服务，满足合规保留要求。

### 4.2 存储容量规划

日志存储容量应按以下公式估算：

1. 日均日志量：评估各系统日志产生量，计算日均总量。
2. 压缩比：通常日志压缩比为 5:1 至 10:1。
3. 保留周期：按存储策略确定各级存储的保留周期。
4. 冗余系数：预留 30% 冗余空间应对突发日志量。

### 4.3 数据安全

日志数据应实施以下安全措施：

1. 传输加密：日志传输应使用 TLS 1.2 及以上协议。
2. 存储加密：日志存储应使用 AES-256 加密。
3. 访问控制：日志查询应实施基于角色的访问控制。
4. 防篡改：关键日志应使用区块链或数字签名技术防篡改。
5. 审计记录：对日志的查询和导出操作应记录审计日志。

## 5. 日志分析

### 5.1 实时分析

实时分析应支持以下场景：

1. 安全告警：实时检测异常登录、暴力破解、SQL 注入等安全事件。
2. 性能告警：实时监控应用响应时间、错误率和资源使用率。
3. 业务告警：实时监控关键业务指标和交易异常。
4. 合规告警：实时检测敏感数据访问、权限变更等合规事件。

### 5.2 离线分析

离线分析应支持以下场景：

1. 安全调查：对安全事件进行溯源分析和影响评估。
2. 性能优化：分析系统性能瓶颈和优化建议。
3. 容量规划：分析资源使用趋势和容量预测。
4. 合规审计：生成合规审计报告和证据材料。

### 5.3 关联分析

关联分析应支持跨数据源的事件关联：

1. 跨系统关联：关联不同系统中同一用户的操作日志。
2. 跨时间关联：关联时间窗口内的相关事件。
3. 跨层级关联：关联网络层、应用层和数据层的事件。
4. 威胁情报关联：将内部日志与外部威胁情报进行关联。

## 6. 告警管理

### 6.1 告警规则

告警规则应覆盖以下场景：

1. 安全类告警：多次登录失败、异常时间访问、大量数据导出、敏感文件访问。
2. 运维类告警：服务器宕机、磁盘空间不足、CPU 使用率过高、网络延迟异常。
3. 业务类告警：交易失败率突增、订单量异常、支付超时、库存异常。
4. 合规类告警：权限违规变更、数据删除操作、审计日志被修改。

### 6.2 告警分级

告警按紧急程度分为四级：

1. P1 紧急：确认的安全入侵或核心系统故障，15 分钟内响应。
2. P2 高危：可疑的安全事件或重要系统异常，1 小时内响应。
3. P3 中危：安全策略违规或一般系统告警，4 小时内响应。
4. P4 低危：信息类告警，24 小时内响应。

### 6.3 告警通知

告警通知应通过以下渠道发送：

1. 即时通讯：通过企业微信或钉钉发送告警通知。
2. 短信通知：P1 和 P2 告警应发送短信通知。
3. 邮件通知：所有告警应发送邮件通知。
4. 电话通知：P1 告警应自动触发电话通知。

## 7. 可视化与报表

### 7.1 仪表盘

日志分析平台应提供以下标准仪表盘：

1. 安全态势仪表盘：展示安全事件趋势、攻击类型分布和威胁地图。
2. 运维监控仪表盘：展示系统健康状态、资源使用率和性能指标。
3. 业务监控仪表盘：展示交易量趋势、业务异常和用户行为分析。
4. 合规审计仪表盘：展示合规事件统计、审计发现和整改进度。

### 7.2 报表管理

日志分析平台应支持以下报表：

1. 日报：每日安全态势、运维状态和业务概况。
2. 周报：每周安全趋势、运维统计和异常分析。
3. 月报：每月安全审计、容量分析和合规报告。
4. 专项报告：安全事件调查报告、合规审计报告和性能优化报告。

## 8. 合规要求

### 8.1 等保要求

日志分析平台应满足等级保护 2.0 的以下要求：

1. 日志记录：应记录用户操作、安全事件和系统运行日志。
2. 日志保护：日志应受到保护，防止未授权删除、修改或覆盖。
3. 日志保留：日志保留期限不少于 6 个月。
4. 日志审计：应定期对日志进行审计分析。

### 8.2 行业合规

特定行业应满足的日志合规要求：

1. 金融行业：交易日志保留不少于 5 年，操作日志保留不少于 3 年。
2. 电信行业：用户上网日志保留不少于 6 个月。
3. 医疗行业：电子病历访问日志保留不少于 15 年。
4. 政务系统：政务操作日志保留不少于 3 年。

## 9. 运维管理

### 9.1 平台运维

日志分析平台的运维应关注以下方面：

1. 集群健康：监控 Elasticsearch 集群状态、节点健康和分片状态。
2. 性能监控：监控查询延迟、索引速率和存储使用率。
3. 容量管理：定期评估存储容量，及时扩容。
4. 版本管理：定期升级平台组件，修复安全漏洞。

### 9.2 数据质量

日志数据质量应持续监控：

1. 完整性：检查日志采集是否完整，是否有丢失。
2. 准确性：检查日志解析是否准确，字段映射是否正确。
3. 及时性：检查日志采集延迟是否在可接受范围内。
4. 一致性：检查同一来源的日志格式是否一致。

## 10. 附则

本规范由信息安全部和运维部共同负责解释和修订，自发布之日起施行。

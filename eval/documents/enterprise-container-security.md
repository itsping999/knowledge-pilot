# 企业容器安全管理规范

## 文档信息
- 文档编号：SEC-CTR-001
- 版本：1.0
- 适用范围：容器化应用开发、部署和运行的全生命周期

## 1. 镜像安全管理

### 1.1 基础镜像选择
企业应建立经审批的基础镜像白名单，所有业务镜像应基于白名单中的基础镜像构建。基础镜像应优先选择精简发行版镜像（如 Alpine、Distroless），减少不必要的系统组件和攻击面。基础镜像应由安全团队定期扫描和更新，发现已知漏洞后应在七天内发布修复版本。

### 1.2 镜像构建安全
镜像构建过程应遵循以下安全规范：
- 不得在镜像中硬编码密码、API 密钥、证书私钥等敏感信息
- 应使用多阶段构建，编译阶段和运行阶段分离，减少最终镜像体积
- 应使用非 root 用户运行应用进程
- 应设置只读文件系统层，敏感目录通过挂载卷提供写入能力
- 应删除构建工具、包管理器缓存和临时文件

### 1.3 镜像扫描与签名
所有镜像在推送至镜像仓库前应完成安全扫描，包括已知 CVE 漏洞检测、恶意软件检测和敏感信息检测。严重和高危漏洞应阻断镜像推送，中危漏洞应在七天内修复。镜像应使用 cosign 或 Notary 进行签名，部署时应验证镜像签名的完整性和来源可信性。

## 2. 容器运行时安全

### 2.1 容器隔离
容器应启用以下隔离机制：
- 使用 Linux Namespace 实现进程、网络、文件系统和用户隔离
- 使用 Seccomp 系统调用过滤，限制容器可使用的系统调用
- 使用 AppArmor 或 SELinux 强制访问控制策略
- 限制容器可使用的 CPU、内存和磁盘 I/O 资源
- 禁止容器使用特权模式运行，除非经过安全审批

### 2.2 容器网络策略
容器间网络通信应通过网络策略（NetworkPolicy）进行控制，默认拒绝所有容器间通信。仅允许业务必需的容器间网络访问，并通过标签选择器定义允许规则。容器对外暴露的服务应通过 Ingress 控制器统一管理，不得直接使用 NodePort 或 HostNetwork。

### 2.3 容器存储安全
容器持久化数据应使用加密存储卷。敏感配置信息应通过 Kubernetes Secret 或外部密钥管理系统注入，不得通过环境变量或配置文件明文传递。容器临时文件系统应设置大小限制，防止磁盘空间耗尽攻击。

## 3. Kubernetes 集群安全

### 3.1 集群访问控制
Kubernetes API Server 应启用 RBAC 授权和准入控制。管理员访问应通过堡垒机或多因素认证。ServiceAccount 应按最小权限原则配置，禁止使用默认 ServiceAccount 运行业务 Pod。集群管理员权限应严格限制，仅授予必要的运维人员。

### 3.2 Pod 安全策略
企业应启用 Pod Security Standards（PSS），对不同安全级别的命名空间应用不同策略：
- 特权命名空间（如 kube-system）：允许特权操作，仅限集群管理员使用
- 基线命名空间（如生产环境）：禁止特权容器、主机网络和主机路径挂载
- 限制命名空间（如开发测试）：在基线基础上进一步限制卷类型和用户 ID

### 3.3 集群网络安全
集群内部通信应启用 mTLS 加密（如通过 Istio 服务网格）。Etcd 数据应加密存储，访问 Etcd 应使用客户端证书认证。集群组件之间的通信应使用安全端口，禁用不安全端口。

## 4. 容器安全监控

### 4.1 运行时威胁检测
应部署容器运行时安全监控工具（如 Falco），检测以下异常行为：
- 容器内启动 shell 或执行未授权命令
- 容器访问敏感文件（如 /etc/shadow、/proc/kcore）
- 容器建立异常网络连接（连接矿池、C2 服务器）
- 容器内文件被异常修改（Webshell 植入）
- 容器资源使用异常（挖矿行为）

### 4.2 安全日志
容器安全日志应包括镜像拉取记录、容器创建和销毁事件、安全策略违规事件、运行时告警事件和集群管理操作审计。日志应发送至集中日志平台并保留九十天以上。

## 5. 容器安全应急响应

### 5.1 应急处置流程
发现容器安全事件后应执行以下处置流程：
- 隔离受影响的容器和 Pod，断开网络连接
- 保留容器运行状态用于取证分析
- 检查同一集群内是否存在同类风险
- 分析攻击路径和影响范围
- 修复漏洞或配置缺陷后重新部署
- 复盘总结并更新安全策略

### 5.2 容器逃逸应急
发生容器逃逸事件时应立即隔离受影响的宿主机，检查宿主机是否被进一步入侵。应评估同一宿主机上其他容器是否受到影响。应审查容器安全策略是否存在配置缺陷。

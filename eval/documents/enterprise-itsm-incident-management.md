# 星河制造集团 IT 服务管理规范（样例）

## 1. 总则

为规范集团 IT 服务管理流程，提升 IT 服务质量和用户满意度，确保 IT 基础设施和应用系统的稳定运行，依据 ITIL 4 框架和 ISO/IEC 20000 标准，结合集团实际情况，制定本规范。本规范适用于集团信息技术部及各子公司 IT 部门的所有 IT 服务管理活动。

## 2. 服务目录管理

### 2.1 服务目录定义

IT 服务目录是集团所有 IT 服务的标准化清单，包含服务名称、服务描述、服务级别目标、服务负责人、计费方式和服务开通条件等信息。服务目录分为面向业务用户的服务目录和面向 IT 内部的技术服务目录两类。

### 2.2 服务分类

IT 服务按业务属性分为以下类别：

1. 基础设施服务：包括网络接入、服务器托管、存储分配、域名解析和 VPN 接入等。
2. 终端服务：包括桌面设备配置、软件安装、外设支持、移动设备管理和远程桌面等。
3. 应用服务：包括 ERP 系统、CRM 系统、OA 系统、邮件系统和自研业务系统的使用支持。
4. 数据服务：包括数据库管理、数据备份恢复、数据仓库运维和商业智能报表等。
5. 安全服务：包括漏洞扫描、渗透测试、安全加固、安全培训和安全事件响应等。
6. 云服务：包括公有云资源管理、私有云运维和混合云架构支持等。

### 2.3 服务级别管理

每个 IT 服务应定义明确的服务级别目标（SLO），包括：

1. 可用性目标：核心系统不低于 99.9%，重要系统不低于 99.5%，一般系统不低于 99%。
2. 响应时间目标：P1 事件 15 分钟内响应，P2 事件 30 分钟内响应，P3 事件 4 小时内响应，P4 事件 8 小时内响应。
3. 恢复时间目标：核心系统 RTO 不超过 4 小时，重要系统 RTO 不超过 8 小时，一般系统 RTO 不超过 24 小时。
4. 容量目标：系统资源使用率不超过 70%，存储容量预留不低于 30%。

## 3. 事件管理

### 3.1 事件分类

IT 事件按影响范围和紧急程度分为四级：

1. P1 紧急事件：核心业务系统中断，影响全公司或主要业务线的正常运营。示例：ERP 系统宕机、生产网络中断、邮件系统全面不可用。
2. P2 高危事件：重要系统功能异常，影响部分业务线或多个部门。示例：CRM 系统性能严重下降、VPN 连接间歇性中断、报表系统数据延迟。
3. P3 中危事件：一般系统功能异常，影响个别用户或单个部门。示例：个别用户无法登录系统、打印机故障、单个模块功能异常。
4. P4 低危事件：非紧急问题或服务请求。示例：密码重置、软件安装申请、使用咨询。

### 3.2 事件响应流程

事件响应流程包括以下阶段：

1. 事件检测与记录：通过监控系统自动告警或用户报障发现事件，创建事件工单记录事件详情。
2. 事件分类与优先级：根据影响范围和紧急程度确定事件优先级，分配至相应支持团队。
3. 初步诊断与升级：一线支持团队进行初步诊断，无法解决的事件升级至二线专家团队，P1 事件直接升级至技术总监。
4. 事件解决与恢复：执行解决方案恢复服务，验证服务恢复正常。
5. 事件关闭与回顾：记录解决方案和根因分析，P1/P2 事件进行事后回顾。

### 3.3 事件升级机制

事件升级分为技术升级和管理升级两类：

技术升级：一线无法解决时升级至二线专家，二线无法解决时升级至三线厂商或开发团队。P1 事件同时通知架构师团队。

管理升级：P1 事件发生 30 分钟未解决时通知 IT 总监，1 小时未解决时通知 CIO，4 小时未解决时通知分管副总裁并启动危机管理流程。

### 3.4 重大事件回顾

P1 和 P2 事件解决后，应在 5 个工作日内组织事后回顾会议（Post-Incident Review），输出以下成果：

1. 事件时间线：记录事件从发现到解决的完整时间线。
2. 根因分析：使用 5 Why 方法或鱼骨图分析事件根本原因。
3. 改进措施：制定技术改进、流程改进和预防措施的行动计划。
4. 经验教训：总结事件处理过程中的经验教训，更新知识库。

## 4. 问题管理

### 4.1 问题识别

问题管理通过以下途径识别潜在问题：

1. 事件趋势分析：分析重复发生或频繁发生的事件模式。
2. 重大事件根因分析：从重大事件中识别系统性问题。
3. 主动问题发现：通过容量规划、性能监控和架构评审发现潜在风险。
4. 用户反馈分析：从用户投诉和满意度调查中识别服务质量问题。

### 4.2 问题分析方法

问题分析应采用以下方法：

1. 5 Why 分析法：连续追问五个为什么，找到根本原因。
2. 鱼骨图分析法：从人员、流程、技术、环境四个维度分析问题原因。
3. 故障树分析法：对复杂系统故障进行逻辑推理分析。
4. 关联分析法：分析多个事件之间的关联关系，发现共性问题。

### 4.3 问题解决与知识库

已知错误（Known Error）应记录在已知错误数据库中，包含问题描述、临时解决方案和永久修复计划。解决方案应同步更新至知识库，供一线支持团队参考。

## 5. 变更管理

### 5.1 变更分类

IT 变更按风险级别分为三类：

1. 标准变更：低风险、预审批的常规变更。示例：密码策略更新、补丁定期安装、用户权限调整。
2. 普通变更：中等风险、需要 CAB 审批的变更。示例：应用版本升级、数据库参数调整、网络配置变更。
3. 紧急变更：高风险或紧急情况下的变更。示例：安全漏洞紧急修复、生产故障修复、监管合规紧急整改。

### 5.2 变更审批流程

普通变更审批流程：

1. 变更申请：变更申请人填写变更请求单，说明变更原因、内容、影响范围和回滚方案。
2. 技术评审：技术评审委员会评估变更的技术可行性和风险。
3. CAB 审批：变更咨询委员会（CAB）审批变更请求，评估业务影响。
4. 变更排期：确定变更实施时间窗口，通知受影响的业务部门。
5. 变更实施：按变更计划执行变更，记录变更过程。
6. 变更验证：验证变更是否成功实施，服务是否恢复正常。
7. 变更关闭：更新配置管理数据库（CMDB），关闭变更工单。

### 5.3 变更风险评估

变更风险评估应考虑以下因素：

1. 技术复杂度：变更涉及的技术复杂程度和依赖关系。
2. 影响范围：变更影响的用户数量和业务系统。
3. 回滚难度：变更失败后回滚的难度和时间。
4. 历史记录：类似变更的历史成功/失败记录。
5. 时间窗口：变更实施时间对业务的影响。

## 6. 配置管理

### 6.1 CMDB 管理

配置管理数据库（CMDB）应记录所有 IT 配置项（CI）的信息，包括：

1. 硬件配置项：服务器、存储设备、网络设备、终端设备等。
2. 软件配置项：操作系统、数据库、中间件、应用软件等。
3. 文档配置项：架构文档、操作手册、合同协议等。
4. 服务配置项：服务目录、SLA 合同、服务报告等。

### 6.2 配置项关系

CMDB 应记录配置项之间的关系，包括：

1. 依赖关系：服务依赖的应用、应用依赖的中间件、中间件依赖的服务器。
2. 连接关系：网络设备之间的连接、服务器与存储的连接。
3. 组成关系：集群由多台服务器组成、应用由多个模块组成。
4. 影响关系：配置项变更对其他配置项的影响。

## 7. 服务级别管理

### 7.1 SLA 管理

服务级别协议（SLA）应明确以下内容：

1. 服务范围：SLA 覆盖的服务和不覆盖的服务。
2. 服务目标：可用性、响应时间、恢复时间等量化目标。
3. 服务时间：标准服务时间和扩展服务时间。
4. 职责分工：IT 部门和业务部门各自的职责。
5. 报告机制：服务报告的频率和内容。
6. 处罚机制：未达到 SLA 目标的补偿措施。

### 7.2 服务报告

IT 部门应定期发布服务报告，内容包括：

1. 服务可用性报告：各系统的实际可用性与目标对比。
2. 事件统计报告：事件数量、分类、响应时间和解决时间统计。
3. 变更统计报告：变更数量、成功率和回滚率统计。
4. 容量使用报告：服务器、存储和网络的使用率和趋势。
5. 用户满意度报告：用户满意度调查结果和改进措施。

## 8. 知识管理

### 8.1 知识库建设

IT 知识库应包含以下类型的知识：

1. 已知错误解决方案：常见问题的解决方案和临时规避措施。
2. 操作手册：系统运维操作的标准流程和步骤。
3. 架构文档：系统架构设计和部署拓扑。
4. FAQ 文档：用户常见问题的解答。
5. 培训材料：技术培训和用户培训的材料。

### 8.2 知识共享

知识共享应通过以下方式进行：

1. 事件回顾会议：分享重大事件的处理经验和教训。
2. 技术分享会：定期组织技术分享，推广最佳实践。
3. 知识库检索：支持关键词搜索和分类浏览。
4. 社区论坛：建立 IT 社区论坛，促进经验交流。

## 9. 工具与平台

### 9.1 ITSM 平台

集团应建立统一的 ITSM 平台，支持以下功能：

1. 工单管理：事件、问题、变更和服务请求的全生命周期管理。
2. CMDB 管理：配置项的录入、查询和关系管理。
3. 知识库管理：知识的创建、审核、发布和检索。
4. 自助服务门户：用户自助提交工单、查询进度和检索知识。
5. 报表与分析：服务报告、趋势分析和绩效看板。

### 9.2 监控平台

集团应建立统一的监控平台，覆盖以下层面：

1. 基础设施监控：服务器 CPU、内存、磁盘和网络监控。
2. 应用性能监控：应用响应时间、错误率和吞吐量监控。
3. 业务监控：关键业务流程和交易成功率监控。
4. 日志监控：系统日志和安全日志的集中收集和分析。

## 10. 持续改进

### 10.1 改进框架

IT 服务管理采用 PDCA（计划-执行-检查-改进）循环持续改进：

1. 计划阶段：识别改进机会，制定改进计划。
2. 执行阶段：实施改进措施，记录改进过程。
3. 检查阶段：评估改进效果，对比改进前后的指标。
4. 改进阶段：固化有效改进，推广最佳实践。

### 10.2 改进指标

IT 服务管理改进应关注以下指标：

1. 事件平均解决时间（MTTR）：目标逐月缩短。
2. 事件复发率：目标逐月降低。
3. 变更成功率：目标不低于 95%。
4. 用户满意度：目标不低于 85 分。
5. 服务可用性：核心系统目标不低于 99.9%。

## 11. 附则

本规范由信息技术部负责解释和修订，自发布之日起施行。
